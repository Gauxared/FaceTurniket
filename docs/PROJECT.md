Авто-турникет

Система идентификации сотрудника/студента по фото для прохода через турникет.

Цель

Разработать локальный прототип системы контроля доступа, которая по изображению лица определяет пользователя, проверяет его право на проход и принимает решение об открытии турникета.

Основной сценарий
Человек подходит к турникету.
Камера получает серию кадров.
Система выбирает лучший кадр.
Система проверяет наличие лица и качество изображения.
Система получает embedding лица.
Система сравнивает embedding с сохранёнными шаблонами.
Система проверяет право доступа пользователя.
Если всё успешно — турникет открывается.
В журнал записывается событие.
Важное архитектурное решение

Система не обучает собственную модель распознавания лиц с нуля.

Вместо этого используется готовая face-recognition библиотека, подключённая через provider/adapter.

На первом этапе используется mock provider, чтобы проверить архитектуру, бизнес-логику, harness и тесты без зависимости от реального ML.

Почему не обучается модель по пользователям

Не нужно делать классификатор, где каждый студент или сотрудник является отдельным классом.

Такой подход плох, потому что:

пользователи часто добавляются и удаляются;
для каждого человека потребовалось бы много фото;
при добавлении нового человека модель пришлось бы дообучать;
такую систему сложнее сопровождать.

Вместо этого используется подход face embedding:

при регистрации пользователя создаётся embedding-шаблон;
при проходе создаётся новый embedding;
новый embedding сравнивается с шаблонами из базы.

Enrollment and identity store:

при enrollment изображение проходит через recognition pipeline;
при успешном качестве создаётся face template с mock embedding;
template хранится в InMemoryTemplateStore;
при 1:1 verification embedding сравнивается с шаблонами claimed user;
при 1:N identification embedding сравнивается со всеми шаблонами.
Режимы работы
Основной режим MVP: mock identification

На раннем этапе система не использует реальное распознавание лица.

Mock provider возвращает заранее заданный recognition_result по имени файла или fixture-данным.

Выбор провайдера через FACE_PROVIDER или ProviderFactory:
- "mock" (default) — детерминированный mock
- "insightface" — реальное распознавание через InsightFace (требуется pip install insightface onnxruntime)

Рекомендуемый реальный режим: 1:1 verification

Пользователь сначала предъявляет карту, QR-код, NFC или другой идентификатор.

После этого система проверяет, соответствует ли лицо заявленному пользователю.

Этот режим предпочтителен при большой базе студентов или сотрудников.

Дополнительный режим: 1 identification

Система ищет пользователя по всей базе лиц.

Этот режим можно реализовать позже, но он менее надёжен для большой базы, особенно если у каждого пользователя есть только одно паспортное фото.

Controlled capture

Система не должна пытаться распознать лицо с любого произвольного ракурса.

Предполагается контролируемая точка съёмки:

камера находится перед пользователем;
рядом есть подсказка “Посмотрите в камеру”;
система получает серию кадров;
выбирается лучший кадр;
плохой кадр не используется для допуска.
Quality gate

Перед распознаванием кадр должен пройти проверку качества.

Проверяется:

лицо найдено;
лицо одно;
лицо достаточно крупное;
нормальная резкость;
нормальное освещение;
нет сильного поворота головы;
нет сильного наклона головы;
глаза и основные черты лица видны;
нет признаков spoof-попытки.

Если кадр плохой, система должна вернуть retry или deny, но не allow.

MVP

В MVP входит:

структура проекта;
контракты данных;
mock face recognition provider;
harness-сценарии;
access decision logic;
mock turnstile;
event log;
тесты;
локальный запуск.

В MVP не входит:

физический турникет;
реальная камера;
полноценный liveness detection;
production-база данных;
обучение собственной ML-модели;
хранение реальных биометрических данных.
Основной pipeline

camera/mock image series
→ quality gate (select best frame)
→ face recognition provider
→ recognition_result
→ access decision
→ mock turnstile
→ event log
→ harness report
