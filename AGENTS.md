# AGENTS.md

Этот файл содержит правила для AI-агента, который разрабатывает проект в одиночном режиме.

## Главное правило: экономить контекст

Работа идёт маленькими независимыми итерациями. Агент НЕ должен загружать весь проект и всю документацию перед каждой задачей.

Перед любой задачей обязательно прочитать только:

1. `AGENTS.md`;
2. `docs/CURRENT_STATE.md`;
3. конкретный файл текущей задачи из `tasks/`.

После этого прочитать только файлы, перечисленные в разделе `Required context` текущего task-файла.

Не читать автоматически `docs/PROJECT.md`, `docs/CONTRACTS.md`, `docs/ITERATION_PLAN.md`, README и большие исходные файлы, если текущая задача прямо этого не требует.

Использовать точечный поиск и чтение конкретных файлов вместо полного обхода репозитория.

## Описание проекта

Проект — локальная Python-система идентификации или верификации сотрудника/студента по фото или видео лица для принятия решения о проходе через турникет.

Основной поток:

1. получить изображение или кадры видео;
2. найти лицо;
3. проверить качество;
4. выполнить liveness-проверку или mock-liveness в MVP;
5. получить embedding через face-recognition provider;
6. сопоставить embedding с шаблонами;
7. проверить право доступа;
8. принять решение `allow`, `deny`, `retry` или `manual_check`;
9. передать решение mock-турникету;
10. записать событие в журнал.

## Архитектурные ограничения

- Не обучать модель распознавания лиц с нуля.
- Реальное распознавание подключать только через provider/adapter.
- Сохранять `MockFaceRecognitionProvider` как рабочий вариант.
- Не смешивать ML-логику, бизнес-логику доступа, работу с турникетом и event log.
- ML-модуль не имеет права открывать турникет.
- Access-модуль принимает итоговое решение о проходе.
- Не хранить реальные фото людей, персональные данные и реальные biometric embeddings в репозитории.
- Не использовать пол, возраст, расу, эмоции и похожие признаки для решения о доступе.
- Не менять публичные контракты без обновления соответствующих тестов и документации.
- Не делать широкий рефакторинг вне scope текущей задачи.

## Формат микрозадачи

Каждый task-файл должен по возможности содержать:

- `Goal` — один конкретный результат;
- `Required context` — минимальный список файлов, которые нужно прочитать;
- `Allowed changes` — какие файлы или каталоги разрешено менять;
- `Steps` — 2–6 коротких действий;
- `Checks` — только необходимые для этой итерации проверки;
- `Forbidden` — что нельзя делать;
- `Done criteria` — однозначные критерии завершения;
- `Handoff` — что записать для следующей итерации.

Одна итерация должна решать одну связанную проблему. Если для выполнения задачи требуется одновременно менять несколько несвязанных подсистем, задачу сначала нужно разделить на дочерние task-файлы, а не пытаться выполнить всё одним проходом.

## Рабочий цикл агента

1. Прочитать минимальный стартовый контекст.
2. Кратко записать план из 2–5 пунктов.
3. Реализовать только текущую микрозадачу.
4. Запустить проверки, указанные именно в task-файле.
5. Исправить ошибки в пределах scope задачи.
6. Обновить `docs/CURRENT_STATE.md` коротким handoff-блоком.
7. Завершить работу. Не начинать следующий task в том же контекстном окне.

## Проверки

Не запускать и не анализировать весь проект без необходимости.

- Для маленькой кодовой задачи сначала использовать целевые тесты, указанные в task-файле.
- `scripts/check.ps1` запускать на контрольных checkpoint-задачах или когда task-файл требует полный прогон.
- Для чисто документационной микрозадачи тесты не нужны, если task-файл не требует иного.

## Handoff в `docs/CURRENT_STATE.md`

В конце каждой итерации оставить короткий блок:

```text
Completed: <task id>
Changed: <главные файлы>
Checks: <что запускалось и результат>
Open issues: <только реально оставшиеся проблемы>
Next task: <ровно один следующий task>
```

Не превращать `CURRENT_STATE.md` в подробный журнал рассуждений.

## Definition of Done

Микрозадача считается выполненной только если:

- достигнут ровно один заявленный результат;
- изменения не вышли за `Allowed changes` без технической необходимости;
- выполнены проверки из task-файла;
- публичные контракты не сломаны;
- `docs/CURRENT_STATE.md` обновлён;
- следующий task явно указан;
- агент остановился после текущей итерации.
